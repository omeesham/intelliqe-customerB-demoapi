# QE Playwright Tests — Page Object Model

Human-readable Playwright test suite in a Page Object Model layout. Generated by
JBS IntelliQE. Environment-agnostic, no hardcoded credentials, chromium by
default, runs in parallel, and saves a video + trace for every test.

## Prerequisites

- Node.js 18 or newer

## Install

    npm ci
    npm run install:browsers
    cp .env.example .env
    # then edit .env: set BASE_URL (and APP_USERNAME / APP_PASSWORD if tests sign in)

## Run

    npm test              # headless, chromium
    npm run test:headed   # headed
    npm run test:ui       # interactive UI mode
    npm run report        # open the last HTML report

## Layout

    playwright.config.ts   Playwright config (testDir ./tests, chromium, parallel)
    package.json  tsconfig.json  .env.example
    pages/                 page objects (UI tests)
      base.page.ts         BasePage that every page object extends
      <module>/            e.g. auth/login.page.ts
      components/          shared components
    api/                   service objects (API tests)
      base.api.ts          BaseApi that every service object extends
      <module>/            e.g. users/users.api.ts
    common/                env, db (Azure SQL), test-data loader, fixtures, matchers, logger
    data/testdata/         JSON test data (non-sensitive)
    specs/                 Markdown test plan (basic-operations.md)
    tests/                 one spec per module: <module>/<module>.spec.ts
    report/                HTML + JUnit report output
    traces/                Playwright traces and videos
    logs/                  execution logs
    .github/workflows/     CI (GitHub Actions)

Specs talk to page objects, never to raw selectors. When the UI changes, fix the
page object under pages/, not the tests.

API specs follow the same pattern with service objects: they call methods on a
class under api/ and assert on the response, never building a URL or setting a
header themselves. When an endpoint moves or its auth changes, fix the service
object under api/, not the tests.

## Configuration

All behavior is driven by .env (see .env.example). No code edits are required to
change target environment, parallelism, or browser mode. In CI, BASE_URL,
APP_USERNAME and APP_PASSWORD come from GitHub Actions secrets.

## Database validation (optional)

Tests can assert on the application's Azure SQL database through common/db.ts.
Set the DB_* values in .env (from GitHub Actions secrets in CI), then query from
a spec or page object:

    import { db } from '../../common/db';

    const row = await db.queryOne('SELECT id FROM Orders WHERE ref = @ref', { ref });
    expect(row).not.toBeNull();

The connection pool is shared across the run and closed automatically in global
teardown. The code is unchanged per customer — just point the DB_* secrets at
that customer's Azure SQL database. In CI, allow the runner's IP through the
Azure SQL firewall.
